# ADR-0003: 락 전략 선택 (비관락 vs 낙관락)

## 상태
확정 — Step 1(비관락), Step 2(낙관락) 측정 완료. 이 도메인은 **비관락** 채택.

## 맥락
Step 0에서 락 없는 재고 차감이 lost update로 oversell 900건을 냈다
(confirmed 1000 ≠ 초기재고−remaining 11). 원인은 재고 차감이
read-modify-write인데 원자적이지 않아, 동시 트랜잭션이 같은 초기값을 읽고
서로의 갱신을 덮어쓴 것. 이를 락으로 해결하되 전략을 비교한다.

## 후보안
- (A) DB 비관락 — `SELECT ... FOR UPDATE` (`@Lock(PESSIMISTIC_WRITE)`)
      "충돌한다고 가정, 먼저 잠그고 작업." 재고 행을 잠가 직렬화.
- (B) DB 낙관락 — `@Version` 컬럼 + 충돌 시 재시도 루프
      "설마 겹치겠어? 하고, 커밋 시 버전 불일치면 롤백·재시도."
- (C) UPDATE 원자 차감 — `UPDATE ... SET quantity=quantity-1 WHERE quantity>0`
      락 개념 없이 DB가 원자 처리. 성능 최고지만 "락 전략 비교" 학습목표를 흐림.
- (D) 애플리케이션 락 — `synchronized` 등. 단일 인스턴스만 유효,
      다중 인스턴스에서 무력화 → "왜 분산락이 필요한가" 설명용 반례로만 가치.

## 선택
- Step 1 = (A) 비관락, Step 2 = (B) 낙관락 을 **둘 다 구현하고 측정 비교.**
- 측정 결과 이 도메인(한정 수량 선착순, 단일 재고 행 극한 경합)에는 **비관락 채택.**

## 예측 vs 실측

### 예측 (측정 전 가설)
- 두 전략 모두 oversell 0 / confirmed 100 / remaining 0 → **적중**
- 비관락: 직렬화로 TPS 하락·p95 상승 예상 → **빗나감** (baseline 비교 함정, 아래)
- 낙관락: 고경합에서 재시도 폭증으로 비관락보다 느릴 것 → **적중** (재시도 9,676회)

### 실측 (재고 100, VU 1000, 풀 100 — 전 Step 동일 조건)
| 전략 | confirmed | oversell | remaining | 재시도 | TPS | p95(전체) | p95(성공) |
|---|---|---|---|---|---|---|---|
| Step 0 락없음 | 1000 | 900 | 89 | — | ~436/s | 1.66s | — |
| Step 1 비관락 | 100 | 0 | 0 | 0 | ~687/s | 1.2s | 492ms |
| Step 2 낙관락 | 100 | 0 | 0 | **9,676** | ~80/s | 12.17s | 10.44s |

## 핵심 발견 1 — 낙관락은 고경합에서 재시도가 폭발한다
- 재고 100개를 파는 데 **재시도 9,676회** 발생. 1개 팔 때마다 평균 ~97회 충돌.
- 실제 DB 접근 시도 = 성공 100 + 재시도 9,676 ≈ 9,776회. 필요한 일의 ~98배를 함.
- 그 결과 TPS는 비관락의 약 1/8, p95는 약 10배. 정합성(oversell 0)은 같지만 성능은 참패.
- **교과서 통념("낙관락은 락을 안 잡아 가볍다")은 저경합 전제.** 모두가 단일 재고 행을
  다투는 고경합에서는 재시도 낭비가 폭발해 오히려 비관락보다 훨씬 무겁다.
- 단, 이는 "낙관락이 항상 나쁨"이 아니라 **"이 시나리오(단일 행 극한 경합)에서 나쁨"**이다.
  충돌이 드문 워크로드(예: 넓게 분산된 다수 상품, 낮은 동시성)라면 낙관락이 유리하다.

## 핵심 발견 2 — Step 0 vs Step 1 처리량 비교는 "부당"하다
- 정합성 비교(oversell 900→0)는 공정하다. 프로젝트의 본질이며 함정 없음.
- 처리량 비교(TPS·p95)는 두 버전의 "일의 양"이 달라 부당하다:
  - Step 0: 1000건 전부 DB 쓰기(INSERT+UPDATE) — oversell 하느라 과부하.
  - Step 1: 100건만 DB 쓰기, 900건은 가드에서 즉시 거절 → 쓰기 없음.
- "비관락이 빨라서 687"이 아니라 "Step 0이 oversell로 불필요한 쓰기를 많이 해 느렸던 것".
- 순수 락 비용 비교는 재고를 키워 성공률을 맞춘 뒤 재측정해야 한다(후속 과제).

## 결론
- **이 도메인(한정 수량 선착순)에는 비관락(PESSIMISTIC_WRITE)을 채택한다.**
  근거: 낙관락은 동일 정합성을 내지만 고경합에서 재시도 9,676회로 성능이 8배 이상 나빴다.
- **일반화**: 경합도가 판단 기준이다. 단일 자원에 다수가 몰리는 고경합 → 비관락.
  충돌이 드문 저경합 → 낙관락. 이 프로젝트는 전자의 극단 사례를 숫자로 확인했다.

## 후속 과제 (공정 비교 / 확장)
- 재고를 크게(예: 1000+) 잡아 성공률을 맞춘 뒤 순수 락 직렬화 비용 재측정.
- 부하 지속형 프로파일(duration 기반)로 steady state TPS 측정 (현재 ~12초에 종료).
- (로드맵) Step 3 Redis 원자 차감 / 분산락 — 단일 DB 행 병목을 벗어나는 대안.
