# ADR-0002: HikariCP 커넥션 풀 100

## 상태
채택 (Step 0 baseline 측정부터 적용)

## 맥락
k6로 VU 1,000을 던지지만, 앱→DB 동시 접근은 커넥션 풀 크기가 상한이다.
HikariCP 기본값은 최대 10. 풀이 10이면 1,000개 요청 중 실제로 DB에
동시 도달하는 건 10개뿐이고 나머지는 풀 대기로 직렬화된다.

## 후보안
- (A) 기본 10 유지 → "동시성은 풀 크기에 지배된다"를 발견으로 서술
- (B) 풀을 100으로 확대 → DB 레벨 동시성을 실제로 확보

## 선택
- **(B) 풀 100.** baseline에서 oversell을 확실히 재현하기 위함.

## 버린 이유 / 트레이드오프
- (A)를 지금 버린 이유: 풀이 10이면 read-check-write가 겹치는 창이 좁아
  oversell이 약하게(혹은 0으로) 재현될 수 있다. baseline이 안 터지면
  이후 모든 Step의 "전/후 비교"가 근거를 잃는다. 그래서 먼저 확실히 터뜨린다.
- 트레이드오프: 풀을 키우면 병목이 **"커넥션 풀 대기"에서 "DB 행 락 경합"으로 이동**한다.
  즉 동시성 강도는 풀 크기가 지배한다 — 이 사실 자체가 관찰 포인트.
- 전제: MySQL 8 기본 max_connections=151. 풀 100은 수용 가능.
  풀을 200+ 로 올리면 docker-compose의 MySQL max_connections도 함께 올려야 한다.
- (A)는 폐기가 아니라 **후속 실험으로 보류**: 풀 크기를 10/50/100/200으로 바꿔가며
  oversell·TPS 변화를 측정하면 "동시성이 풀에 지배된다"를 정량 증명할 수 있다.

## 측정값 (Step 0, 풀=100)
- oversell: 900건 (재고 100 / confirmed 1000)
- TPS: ~436/s
- p95: 1.66s (http_req_duration)
- 면접 예상 질문: "동시 1,000인데 실제 동시성은 풀=100 아닌가?" → 맞다.
  이 baseline은 절대 성능이 아니라 **Step 간 상대 비교용 기준선**이다.
